## Deployment layout

- App: `garmin-mcp-mikemurphysmind`, personal organization, `iad` region.
- MCP URL: `https://garmin-mcp-mikemurphysmind.fly.dev/mcp`.
- One Machine, at most one active instance, 1 shared CPU, 512 MB RAM, and a
  1 GB encrypted volume. It stops when idle and starts on incoming requests.
- Fly terminates HTTPS; Garmin listens on `0.0.0.0:8080`.
- `/readyz` checks SQLite readiness; `/livez` checks the process.
- Mount `garmin_data` at `/data`; state lives in `/data/garmin`.
- The entrypoint creates only a new state directory, then drops to UID/GID
  `65532:65532`. It refuses a missing mount or unexpected existing ownership/mode.
- Both mutating tool tiers are disabled by command-line flags, which outrank
  environment settings. No Garmin application source has been changed.

`Dockerfile` at the repository root remains the upstream runtime-only image.
`deploy/fly/Dockerfile` builds the binary from source with the Go version in
`go.mod`. Its Alpine runtime includes a shell and `su-exec` solely to initialize
Fly's root-owned volume before running the server unprivileged. Base images are
pinned by multi-platform digest. The Dockerfile-specific ignore file allowlists
source inputs so local state and Git metadata do not reach the remote builder.

The master key is generated by Garmin MCP on first start. The configured
`master-key-file` names `/data/garmin/keys/key-v1.json`; upstream uses the
*parent directory* to locate all key versions and the active-version marker.
Never regenerate or replace this key while retaining the database.

## Cost and idle shutdown

`auto_stop_machines = "stop"`, `auto_start_machines = true`, and
`min_machines_running = 0` let Fly stop the single Machine when it has no
traffic, then start that same Machine for the next request. Fly checks every
few minutes; this is not a fixed idle timeout. Long-lived MCP connections or
frequent requests can keep it running. Expect a short startup delay and let the
client reconnect after an in-memory MCP session expires. Stored Garmin tokens,
OAuth grants, and encryption keys remain on the mounted volume across stops.
Browser login sessions and pending Garmin MFA continuations are in-memory;
stopping the Machine invalidates an unfinished login. Start again with Connect
in ChatGPT if a stop occurs during the browser flow.

At the published `iad` rates checked on 2026-09-19, 512 MB shared CPU compute is
about $3.19 per 30 days if continuously running. The 1 GB volume costs $0.15 per
month even while stopped. If the Machine runs for 10% of the month, those two
items total about $0.47 instead of $3.34. This is an illustration, not a billing
cap: actual running time depends on incoming traffic. Stopped-image storage,
bandwidth, billable snapshots, taxes, and account credits can affect the total.
Stopped root filesystems cost $0.15/GB-month; this runtime image is small.
Keep 512 MB until real authenticated requests establish peak memory use; idle
memory alone does not establish a safe lower limit.

For a configuration-only change, reuse the existing runtime image to avoid a
remote rebuild:

```sh
fly machine list --json
# Copy the current Machine's config.image into <existing-runtime-image>.
fly deploy --image <existing-runtime-image> --ha=false
```

After the Machine has been idle for a few minutes, inspect `fly machine list`
without making HTTP requests. It should become `stopped`. A request to
`/readyz` should start it and return 200; unauthenticated `/mcp` must still
return 401. Keep the same Machine and volume. Do not add an external uptime
monitor that continually wakes it. If cold starts cause client trouble, restore
`auto_stop_machines = "off"` and `min_machines_running = 1`, then redeploy.

## OAuth and secrets

Garmin MCP is its own OAuth 2.1 authorization server. It requires an explicitly
registered client and PKCE S256. It has no dynamic client registration and no
Google/OpenID Connect login integration. Google Console credentials alone do
not enable Google login. Keep that separate from the Garmin account login.

**Current connection:** use client ID `chatgpt` and leave the client secret blank.
The public client is bound to the exact ChatGPT callback and mandatory PKCE S256;
it does not permit anonymous Garmin data access. Garmin login and the account
allowlist still apply. The current registry permits `garmin:read` and
`offline_access`; server-side write/destructive tiers remain disabled.

The helper described below is an alternative **confidential-client** setup that
requires a client secret. Running it replaces the current registry and requires
updating the ChatGPT connection to use that same secret. Keep the current public
client unless deliberately making that change.

Set these using Fly secrets, never checked-in configuration:

- `GARMIN_MCP_OAUTH_CLIENTS`: JSON client registry; the helper registers a
  confidential `chatgpt` client with only `garmin:read` and `offline_access`.
- `GARMIN_MCP_LOGIN_ALLOWED_EMAILS`: your permitted Garmin account address.

The helper sends the SHA-256 **digest** of your client secret; the server never
needs the raw client secret. Keep the original in your password manager and use
it in ChatGPT. Garmin email/password/MFA are entered in the HTTPS Garmin login
form; the server stores the resulting Garmin tokens encrypted in SQLite.

Run with Python 3.11 or newer in your own terminal:

```sh
python3 deploy/fly/configure-oauth.py
```

The prompts do not write input to files or put it in process arguments. Email
and client-secret prompts are hidden. Changes are staged; a deploy applies them.
The helper replaces the entire registry with the one ChatGPT client. If you later
add other clients, manage the full registry rather than rerunning this helper.

Copy the exact callback URL from ChatGPT's MCP app management page. Do not guess
it. Current OpenAI documentation uses a per-connection path unless the server
implements RFC 9207 issuer identification; this upstream build does not advertise
that feature. Keep redirect wildcards disabled. The helper accepts the documented
`https://chatgpt.com/connector/oauth/...` and stable callback forms, but you must
supply the exact value your connection displays.

If ChatGPT must first reach a live endpoint to reveal its callback, bootstrap
with a synthetic public client `deployment-check`, exact loopback redirect
`http://127.0.0.1:8765/callback`, scope `garmin:read`, and the MCP resource URL
above. Set the login allowlist to `pending-setup@example.invalid`. This permits
startup and OAuth discovery while blocking real Garmin logins. Replace **both**
secrets with the helper before attempting account authorization. Never leave the
login allowlist empty: upstream interprets that as allowing any Garmin account.

## First deployment

After authenticating `gh` and `fly`, from the repository root:

```sh
fly config validate
fly apps create garmin-mcp-mikemurphysmind --org personal
fly volumes create garmin_data --app garmin-mcp-mikemurphysmind --region iad --size 1 --snapshot-retention 7
# Configure real OAuth secrets, or the blocked-login bootstrap described above.
fly deploy --remote-only --ha=false
fly machine list
fly volumes list
fly checks list
```

`--ha=false` is required on the first deployment so Fly does not create a spare
Machine. `min_machines_running = 0` permits idle shutdown; it is not a maximum.
Keep exactly one Machine and one volume; never scale horizontally or clone an
active Machine. The
`immediate` deployment strategy accepts a short outage instead of requiring
another active application instance. Do not add a `release_command`: it runs in
a separate temporary Machine without this application's mounted volume.

Public IPv4/IPv6 addresses are allocated by Fly on the first HTTP deployment.
Use `fly ips list` to inspect them. The trusted proxy setting is scoped to
Fly's documented immediate IPv4 proxy subnet `172.19.0.0/16`. It does not trust
all private networks or `0.0.0.0/0`. Upstream reads X-Forwarded-For from the
right. Fly documents its public app IP as the last hop; with the conservative
subnet-only setting, OAuth rate limits can be shared under that app IP. If this
matters, verify the actual chain and add only the app's exact IP CIDRs, never a
broad public network. This does not affect OAuth issuer or audience: those come
only from `GARMIN_MCP_PUBLIC_URL`.

## Verify and connect ChatGPT

```sh
curl --fail https://garmin-mcp-mikemurphysmind.fly.dev/livez
curl --fail https://garmin-mcp-mikemurphysmind.fly.dev/readyz
curl --fail https://garmin-mcp-mikemurphysmind.fly.dev/.well-known/oauth-protected-resource
curl --fail https://garmin-mcp-mikemurphysmind.fly.dev/.well-known/oauth-authorization-server
curl -i https://garmin-mcp-mikemurphysmind.fly.dev/mcp
```

Expect `200` from the first four and `401` with a `WWW-Authenticate` challenge
from unauthenticated `/mcp`. Check resource is the complete HTTPS `/mcp` URL,
issuer is the bare HTTPS origin, scopes contain no Garmin write/destructive
scope, and code-challenge methods include `S256`.

In the current ChatGPT connection, use the MCP URL, OAuth, client ID `chatgpt`,
and a blank client secret. The exact callback and account allowlist are already
deployed; retry Connect to start a fresh authorization. For a future confidential
client configured with the helper, use its chosen secret instead. Complete Garmin
login/MFA and consent yourself. Then ask for `server_info` and check effective write and
destructive tiers are disabled, followed by one small read such as a recent
activity or daily summary. Verify reconnect/refresh after the initial session.
A healthy HTTP endpoint does not establish a completed Garmin authorization or
a working ChatGPT connector; record those results separately.

No CORS origins are configured: backend MCP calls with no Origin are allowed;
unlisted browser origins are rejected. If a client actually sends an Origin,
add only that exact origin using `GARMIN_MCP_ALLOWED_ORIGINS`.

## Current MFA troubleshooting

The first real login reached Garmin's verification-code prompt, then ended with
"Nothing here" immediately after submission. The Machine did not restart during
that attempt. The web log records only a terminal login failure. Upstream's
feasibility ADR records live tests without MFA;
its MFA continuation was covered with a fake Garmin service.

An ignored local helper, `.private/diagnose-garmin-login.py`, prepares a private
terminal diagnostic using the already-deployed `auth --tty` command. It isolates
all state in a temporary directory and removes it on exit, while using the same
Fly egress and Garmin login implementation. It does not link ChatGPT. Share only
the final redacted error/result; never share passwords, OTPs, tokens, or HTTP
payloads. The user ran it and received `garmin verify_mfa
[sso.portal.mfa.verify_code]: bot_challenge (status 403)`. This failure precedes
token exchange and ChatGPT consent. The classifier labels every HTTP 403 as
`bot_challenge`; it does not establish whether the cause is IP reputation,
request/session handling, or another Garmin restriction. Only the final MFA
endpoint error is reported, so the primary endpoint's result is unknown.

The next comparison is `.private/diagnose-garmin-login-local.py`, backed by a Mac
binary built from the same application source and dependency pins as Fly. It
runs `auth --tty` locally with an empty environment, verifies the binary hash,
and deletes its isolated temporary state on exit. Its real login result is
pending. Success would narrow the issue to environment/network differences;
the same failure would warrant investigating the MFA implementation. Neither
diagnostic links ChatGPT. Token-file import exists only in stdio serving and
does not bypass remote account linking. No application patch or live
configuration change has been made for this HTTP 403.

## Storage, recovery, and updates

SQLite, OAuth state, Garmin token ciphertext, and all encryption keys live on
the same volume. Files must be `0600` and private directories `0700`, owned by
`65532:65532`. Container replacement must retain the same volume and key.
A Machine restart invalidates in-memory MCP sessions; clients must reconnect.

Daily Fly snapshots retain seven days. A volume is on one host and is not a
replicated database. Keep a separate protected backup of the database **and all
key files**. Follow upstream `docs/operations.md` for a consistent SQLite backup;
copying a live `.db` alone can omit WAL transactions. Never commit backups.
Restore to an inactive volume and stop the existing instance before switching.

Update the fork without mixing deployment files into `master`:

```sh
git fetch upstream --tags
git switch master
git merge --ff-only upstream/master
git push origin master
git switch fly-deploy
git merge master
# Review upstream config changes, update pinned builder image if Go changes,
# rebuild/test, and back up persistent state before deploying.
fly deploy --remote-only --ha=false
```

`origin` is `mikemurphysmind/garmin-mcp`; `upstream` is
`tamcore/garmin-mcp`. The local `remote.pushDefault` is `origin`.
Do not merge `fly-deploy` back into `master` if the goal is a clean upstream copy.
